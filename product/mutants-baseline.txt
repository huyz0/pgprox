# Surviving mutants that are accepted, with the reason each is accepted.
#
# `scripts/mutants.sh` fails on any survivor that is not in this file. That is
# the whole mechanism: the list may not grow without somebody writing down why.
#
# One entry per line, the key and the reason separated by a tab. The key is the
# crate, the file, the function and the replacement text, with no line number,
# so editing the lines above a mutant does not invalidate its entry.
#
# # Where this list came from
#
# `M10.3` ran the tool for the first time, three milestones after
# `standards/testing.md` started claiming that it ran nightly. It found 89
# survivors out of 950 mutants across the four sans-I/O crates: 720 caught, 137
# unviable, 89 alive. That is an 89% kill rate against line coverage of 96% to
# 99%, which is the gap the standard's own sentence about coverage being a floor
# is about.
#
# Every entry started as `untriaged`, which is not a reason. It is a statement
# that the tool ran before anybody had read its output, which is the honest
# order: the gate protects against new survivors from today, and `M10.4` through
# `M10.8` are the tasks that turn each of these into either a test or a real
# reason. `untriaged` may not be used for anything added after those.
#
# `M10.4` did `pgprox-cache`: ten survivors became one. Six fell to four tests
# about the byte accounting, three more to two tests about the recency index and
# the expiry guard, and the last is a timeout with a reason below. That is what
# this file is for: the count only goes down, and every line that stays says why.
#
# `M10.7` and `M10.10` did `pgprox-proto`. Between them nine survivors fell to
# four tests, and the six that remain are equivalent mutants: programs that
# differ from the original in their text and not in anything they can be made to
# do. That is the answer nobody should reach for first, so each one below
# carries the argument rather than the assertion: two operands with no bit in
# common, a `usize` compared against zero, a guard in front of a callee that
# already guards, an empty match arm that exists to hold a comment, a `continue`
# whose case the code below it drops anyway. An equivalent mutant is a claim
# about the code, and the way to tell one from a missing test is to write down
# why no test could distinguish the two programs, then let a reader disagree.
#
# `M10.16` deleted twenty-three entries without writing a test, which needs
# saying because it is the shape of exactly the thing this file exists to
# prevent. It changed the runner, not the code and not the assertions.
#
# `cargo mutants` gives the whole suite one budget and reports a timeout when it
# runs out. Under `cargo test` there is no per-test timeout, so a mutant that
# makes one test hang costs the run its verdict, and the run says "timeout"
# whether or not another test failed the mutant outright. Twenty-three entries
# in this file said, in various words, that the suite detected the mutant by
# hanging. That was a claim about the runner. Under nextest with a per-test cap
# every one of them is a plain failure with a test name attached.
#
# The count went from thirty-seven to fourteen and no timeout remains anywhere.
# `pgprox-cache` is now clean outright, and `pgprox-route` is down to one
# equivalent. The lesson is narrower than "run nextest": a category the tool
# reports is not a finding until you have read what it is a category of.

pgprox-proto|crates/pgprox-proto/src/backend.rs|select_mechanism_from|<=	equivalent. `rank < seen` becomes `rank <= seen`, which lets a later offer of equal rank replace an earlier one. Equal rank means equal string: `rank` is `supported.iter().position(|w| *w == name)`, so two offers with the same rank matched the same entry by equality and are the same text. Replacing a value with itself is not observable. `M15.6` split this function out so the preference rule could be tested against a list long enough to have an order, and that is what the surrounding tests do; this mutant is about the tie, and the tie has one member
pgprox-proto|crates/pgprox-proto/src/relay.rs|FrameRelay::push_header|>=	equivalent. `capacity() > RETAINED_INSPECT.max(want_inspect)` becomes `>=`, so the shrink also runs when the capacity already equals the bound. `Vec::shrink_to` with a minimum equal to the current capacity has nothing to do. The guard exists to skip a call, not to decide anything, and the mutant only stops it skipping. Re-triage if the body of that branch ever does more than `shrink_to`
pgprox-proto|crates/pgprox-proto/src/backend.rs|conn_id_from_key|^	equivalent. `(u64::from(pid as u32) << 32) | u64::from(secret as u32)`: the left operand's low thirty-two bits are all zero and the right operand's high thirty-two are, so the two operands share no set bit and OR, XOR and ADD agree on every input. pgprox-proto|crates/pgprox-proto/src/relay.rs|FrameRelay::push_body|>=	equivalent. `self.want_inspect > 0` becomes `>= 0` on a `usize`, which is always true, and the body it then runs is `copy = 0.min(take)`, an `extend_from_slice` of an empty slice and a subtraction of zero. The guard is an optimisation, not a decision, and the mutant only removes the optimisation
pgprox-proto|crates/pgprox-proto/src/relay.rs|FrameRelay::push_header|>	equivalent. `self.header_buf.len() < HEADER` becomes `> HEADER`, which never holds: `need` is `HEADER - header_buf.len()` and `take` is `need.min(input.len())`, so the buffer is capped at HEADER exactly. Every partial header therefore falls past the early return to `decode_header`, whose own first line returns `Ok(None)` below five bytes, and the `else` branch returns the same `RelayOutcome` the early return would have. The early return duplicates a check the callee already makes. `M10.10` filed the sibling of this expecting a length field read from a byte that had not arrived; the callee's guard is what makes that impossible. `M15.5` rewrote this function around a fast path for a contiguous header and the argument survives it unchanged, because the mutated line is on the reassembly path, which a partial header still takes
pgprox-proto|crates/pgprox-proto/src/session.rs|SessionState::on_frontend|	equivalent. The deleted arm is `FrontendMessage::Sync => {}`, whose body is empty. Without it `Sync` falls to the guarded arm, and `starts_extended_sequence` lists Parse, Bind, Execute, Describe and Close but not Sync, so it falls again to `_ => {}`. The arm exists to hold the comment above it, which is the reason a reader needs and the compiler does not

# --- pgprox-session ---
pgprox-session|crates/pgprox-session/src/sequence.rs|HeldSequence::may_hold|||	equivalent. The `Parse` arm reads `self.frames.is_empty() && self.step == Step::Nothing`, and those two are the same boolean at every reachable state: `feed` only reaches `may_hold` with an empty buffer for a `Parse` or a `Bind`, `record` and the push into `frames` happen together, and `clear` resets both. `A && A` and `A || A` agree, so the second conjunct is a restatement of the first rather than a second condition
pgprox-session|crates/pgprox-session/src/sequence.rs|begins|true	equivalent. `begins` guards the first frame of a sequence, and making it accept everything only lets a message reach `may_hold`, which with an empty buffer returns true for a `Parse` or a `Bind` and false for every other arm: `Describe` and `Execute` both require `Step::Bound` and the catch-all is false. So the frames the guard would have turned away are turned away one check later, with the same `Held::Send`. The guard is worth keeping for saying so at the top of the function, and no test can distinguish the two programs
pgprox-cluster|crates/pgprox-cluster/src/digest.rs|DigestStore::view_hash|	equivalent, with an expiry. The two mutants delete the `NodeMode::Active => 1` and `NodeMode::Draining => 2` arms, so that mode falls to the `_ => 3` wildcard. `NodeMode` is `#[non_exhaustive]` and has exactly two variants today, so deleting either arm leaves the surviving mapping injective: Active 3 and Draining 2, or Active 1 and Draining 3. `view_hash` promises only that two pods with the same view agree and two with different views differ, and both still hold, so no test inside one build can tell. The expiry is the wildcard's own reason for existing: add a third `NodeMode` and Active or Draining collides with it, two different views hash the same, and split brain stops being detectable. Re-triage this entry when `NodeMode` gains a variant. `M14.14`
pgprox-cluster|crates/pgprox-cluster/src/coordinator.rs|NodeCoordinator::home_draining|false	equivalent by construction, after `M14.16`. `MembershipView::home_node` hashes over `active()`, which excludes draining nodes, so a drain rehomes its tenants the moment it is accepted and the home is never a draining node. The one way the view and the digest store could disagree was `gossip` taking a node's mode from a message the store had rejected as stale; `M14.16` stopped that, and `a_stale_digest_cannot_undo_a_drain_in_the_view` holds it stopped. So this function returns `false` on every reachable input and the mutant cannot be told apart. It is kept rather than deleted, and `shed`'s `HomeDraining` guard with it, because the safety property is then enforced structurally by `home_node` *and* checked, and removing the guard would be a change to the public `ShedReason` for no behavioural gain. Re-triage if `home_node` ever ranks draining nodes, or if a second writer of node mode appears. `M14.16`
pgprox-core|crates/pgprox-core/src/sql.rs|Lexer<'a>::skip_trivia|*	equivalent. `find('\n').map_or(len, |i| i + 1)` becomes `i * 1`, so a line comment is consumed up to the newline rather than past it. `skip_trivia` is a loop whose first branch is `trim_leading_space`, and the very next iteration trims the newline it left behind, so the position where the loop settles is identical for every input. The `+ 1` saves one iteration and decides nothing. `M14.31`
pgprox-core|crates/pgprox-core/src/sql.rs|trim_leading_space|false	equivalent. The guard `Some(byte) if byte.is_ascii() => rest` becomes unreachable, so every input takes the `_ => rest.trim_start()` arm. By that point the byte loop above has already consumed every leading ASCII whitespace character, so `rest` begins with either non-whitespace ASCII, where `trim_start` is a no-op and returns the same string, or a non-ASCII character, which is the arm the mutant forces anyway. The guard is an optimisation that avoids Unicode's tables on the common path, not a decision. The `true` form of this mutant is *not* equivalent and is killed by `leading_space_is_trimmed_whether_it_is_ascii_or_not`, which uses a non-breaking space. `M14.31`
pgprox-core|crates/pgprox-core/src/sql.rs|block_comment_end|<=	equivalent, and the same shape as the `split_block_comment` entry above. pgprox-tls|crates/pgprox-tls/src/lib.rs|assert_fips|Ok(())	equivalent in the build this runs in, which is the point of how it is written. `assert_fips` is `check_fips(FIPS_BUILD, is_fips, which)`, and `FIPS_BUILD` is `cfg!(feature = "fips")`, so in the default build it is `false` and `check_fips` returns `Ok(())` for every input: the function *is* the mutant here. pgprox-config|crates/pgprox-config/src/drain.rs|DrainState::reap|()	equivalent. `reap` clears an expired overlay, and every reader goes through `live_overlay`, which filters on expiry already, so no answer this type gives changes. `M14.11` faced the same shape in `LeaseLedger::reap` and gave it a test-only observer instead, because there the discarded entries accumulate in a `HashMap` that a long-lived leader grows without bound. pgprox-load|crates/pgprox-load/src/report.rs|Histogram::bucket|<=	equivalent, and it is a property of the band arithmetic rather than an accident. The three guards are `micros < FINE_LIMIT`, `< MEDIUM_LIMIT` and `< COARSE_LIMIT`, and each band is sized so its first index continues exactly where the previous band's last index stopped: at `FINE_LIMIT` the fine arm answers `index(10_000)` and the medium arm answers `FINE_BUCKETS + 0`, both 10,000; at `MEDIUM_LIMIT` both answer 19,900; at `COARSE_LIMIT` both answer 25,800, the overflow bucket. Checked at all three boundaries rather than argued from the shape. The bands are seamless, so it does not matter which arm claims the boundary value. `M14.43`
pgprox-load|crates/pgprox-load/src/report.rs|Histogram::bucket|+	equivalent on any platform where `usize` is at least 64 bits. The mutated expression is the `unwrap_or(BUCKETS - 1)` fallback of `usize::try_from(value)`, and the function's own comment says why it is there: "every conversion below is of a value the branch has already bounded, so the fallback is the overflow bucket rather than a case that occurs". On a 64-bit target `usize::try_from(u64)` cannot fail, so no input reaches the fallback and its value cannot be observed. Re-triage if this workspace ever targets a 32-bit platform, where the fallback becomes reachable and the constant matters. The `/` form of the same mutant is the same argument. `M14.43`
pgprox-load|crates/pgprox-load/src/report.rs|Histogram::bucket|/	equivalent, for the reason given against the `+` form of this key: it mutates the unreachable `unwrap_or` fallback of a conversion that cannot fail on a 64-bit target. `M14.43`
pgprox-load|crates/pgprox-load/src/sampler.rs|Rng::weighted|+	equivalent. The mutated expression is `weights.len() - 1`, the value returned when the loop finishes without matching, and the loop cannot finish without matching: `point` is drawn as `below(total)` where `total` is the sum of the weights, so `point < total`, and subtracting each weight in turn must bring it below one of them. The zero-total case returns earlier. The line exists to make the function total rather than to be reached, which is what its comment says. The `/` form is the same argument. `M14.43`
pgprox-load|crates/pgprox-load/src/sampler.rs|Rng::weighted|/	equivalent, for the reason given against the `+` form of this key: it mutates a fallback the loop cannot reach. `M14.43`
pgprox-load|crates/pgprox-load/src/workload.rs|Workload::validate_tenants|>=	equivalent, because the boundary is not representable. The guard is `(total - 1.0).abs() > SHARE_TOLERANCE` with `SHARE_TOLERANCE = 0.001`, so `>` and `>=` differ only when the difference is exactly the `f64` nearest 0.001. For `total` in `[1, 2)` the subtraction `total - 1.0` is exact, so hitting the boundary needs `total` to be exactly `1.0 + 0.001_f64` as a real number, which needs more than 53 significant bits and is not an `f64`; the same argument holds below 1.0 for `1.0 - total`. Checked numerically: `0.75 + 0.251` gives a difference of 0.0009999999999998899, and the next value up gives 0.001000000000000112, with nothing in between. No workload document can reach the case the two operators disagree about. `M14.43`
