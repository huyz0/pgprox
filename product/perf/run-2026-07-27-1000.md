# Scale run: 1000 connections, 27 July 2026

The first run at a thousand connections, and the one every later run compares
against.

## What it was

| | |
| --- | --- |
| Connections | 1000 |
| Duration | 45s |
| Workload | `product/perf/workload.yaml` version 2 |
| Seed | 1 |
| Stack | local (`scripts/scale.sh 1000 --local`) |
| Commit | `0402091` |
| Machine | 20 cores, 31 GB, WSL2 6.18.35.2, PostgreSQL 18.4 |

Local rather than compose, because Docker Desktop was down on this machine.
One node, one Postgres, no replica, everything on the loopback. That flatters
network latency and says nothing about replica routing, and it is the same
proxy code path in every other respect.

The baseline runs at 60 connections rather than 1000, because a thousand
direct connections is not a thing Postgres does and measuring one would be
measuring a database past its connection limit.

## What passes, and what does not

The three properties `scripts/scale.sh` asserts at any connection count all
hold: no failed transactions, the upstream cap never breached, and memory that
moves under load.

The latency does not, and the script does not claim it does, because the
roadmap's target is stated at 100k and this is a thousand. It is recorded here
so it cannot be quietly forgotten: **a p50 of 1.18 seconds through the proxy
against 2.2ms direct is four orders of magnitude away from the target of under
1ms added, and nothing about the workload accounts for it.** Throughput of 512
transactions per second against a demand of roughly 3,600 says the proxy is
the bottleneck, and 30 upstream connections in use out of 60 allowed says it
is not the database. That is M7.23.

## Extrapolation, and what it is worth

19,996 bytes per connection at a thousand connections extrapolates to 1,906 MB
at 100k, against a target of 500. That number is a slope, not a prediction: it
includes the process's own fixed cost spread over a thousand connections, and
the per-connection cost at a hundred thousand is dominated by things this run
is too small to show. The reason to record it is to compare it with the next
run, not to predict the one at 100k.

The roadmap's target stays exactly as written and stays unmet until a run at
100k produces it.
