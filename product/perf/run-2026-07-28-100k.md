# Scale run: 100k connections, 28 July 2026

The first attempt at the roadmap's headline number, on a developer machine.
**It did not hold 100k connections**, and this file is here because what it
found is worth more than the number would have been.

## What was run

| | |
| --- | --- |
| Target | 100,000 client connections on one node |
| Generated by | five `loadgen` containers, 20,000 each, 90s ramp |
| Workload | `product/perf/workload-idle.yaml`, think 30s to 5min |
| Duration | 300s |
| Machine | 20 cores, 31 GB, WSL2, everything in containers on one box |

Five containers because one has 28,231 ephemeral ports and 100,000
connections to a single address needs more than that.

## What happened

| Elapsed | Sockets | Clients registered | RSS | Upstream |
| --- | --- | --- | --- | --- |
| 60s | 67,581 | 28,477 | 677 MB | 40 |
| 120s | 132,374 | 29,553 | 1,679 MB | 26 |
| 180s | 110,542 | 30,310 | 2,340 MB | 18 |
| 240s | 115,572 | 22,207 | 2,823 MB | 12 |

56,169 transactions and 863,630 errors across the five clients. The node held
about 30,000 sessions, not 100,000, and never stopped churning.

## Why, in three parts

**The credential path is the first ceiling, and it is a real defect.** The node
logged `locally-reset streams reached limit (1024)` and clients saw
`authentication service unavailable`. That is the h2 client to the sidecar
running out of concurrent streams under a cold-start herd. The grant cache
collapses repeat lookups, but arrival at 1,100 connections a second with an
empty cache, and again whenever the entry's 60-second TTL expires, produces
more concurrent resolves than one h2 connection will carry. A hundred thousand
connections cannot be authenticated through it as it stands.

**The pool cap refusing work is correct.** `53300` under overload is the node
telling clients to retry, and the upstream count stayed at or under its share
throughout, which is the invariant that matters.

**The shed loop is partly a test artifact and partly a real question.** The
node shed clients toward their home nodes three times, and the load client
reconnects to the same node every time, so the shed produced churn rather than
relief. A real client behind a load balancer would land elsewhere. But it does
say that shedding assumes clients can reach another node, and nothing in the
proxy checks that assumption.

## What the memory says

2.8 GB at ~30,000 registered sessions is 93 KB each, against 7,281 measured on
the same build at 10,000 idle connections. The difference is churn: every
refused or reset connection allocates, and glibc does not return the pages. So
this run says nothing about the per-connection cost, and the 10k measurement
still stands as the number to extrapolate from: 694 MB at 100k.

## What a real attempt needs

- The sidecar path fixed or bounded, which is the first thing that breaks.
- Clients that can reach more than one node, or a single-node test with the
  shed pass disabled, so shedding does not fight the harness.
- The load generator on its own machine. Five containers ramping 100k
  connections while three proxy nodes and three databases share twenty cores
  measures the box, not the proxy.
