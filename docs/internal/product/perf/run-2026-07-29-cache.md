# The cache helps by about seven percent, and does not change the shape

`M9.10`. Whether the query cache is worth having, measured against the
reference workload and against `M7.56`'s finding specifically: a hit avoids an
acquire, so the question was whether contention falls.

```bash
                     SCALE_OUT_DIR=... scripts/scale.sh 500 --local   # control
LOCAL_QUERY_CACHE=5s SCALE_OUT_DIR=... scripts/scale.sh 500 --local   # test
```

Five matched pairs, alternating, on one machine, `workload.yaml` version 3 both
sides. The cache serves the one tenant every token in a scale run carries, with
a 5s TTL and the default 64 MiB budget.

## The numbers

The five-hundred-connection phase, which is the one where the cache could
matter: sixty upstream connections, five hundred clients, and a queue.

| | cache off | cache on | |
| --- | --- | --- | --- |
| p50 | 453,859us | 421,479us | **7.1% better** |
| p99 | 2,712,000us | 2,745,000us | unchanged |
| statements | 47,265 | 48,490 | 2.6% more |
| CPU per statement | 673us | 625us | **7.1% better** |
| upstream connections | 50 of 60 | 50 of 60 | unchanged |
| RSS per connection | 16,760 bytes | 17,590 bytes | 5% worse |

The p50 figure is the mean of five runs each, and no cache-on run was slower
than any cache-off run: the two sets do not overlap. The statement and
per-statement-CPU columns are from the last two pairs only, because the three
before them were taken with the counting bug `M9.16` fixed and their
denominators are missing every hit.

The cache itself, consistent to within half a percent across every run:

| | |
| --- | --- |
| hit rate | 39% of lookups |
| share of all statements | 11% |
| invalidations | 10,700 per run, against 20,000 lookups |

## Why only eleven percent

Two ceilings, and both are in the workload rather than in the cache.

`prepared_fraction` is 0.5, so half of every run goes through the extended
protocol, which `M9.7` does not cache and `M9.12` is about. Those statements
never reach a lookup at all.

Of the half that does, 30% of the workload's statements are writes, and every
one drops the tenant's entire cache. Ten thousand seven hundred invalidations
against twenty thousand lookups is the cache being emptied roughly every other
lookup. A 39% hit rate under that is better than it sounds.

So the reachable ceiling on this workload is about 20% of statements, and 11%
is what a 5s TTL fighting a write every third statement actually gets.

## What it did not do, which is the more useful half

**The p99 did not move.** 2.71s against 2.75s, which is noise. The tail here is
the database's queue: five hundred clients against sixty connections, and the
statements that wait longest are the ones the cache cannot answer. Removing 11%
of the arrivals shortens a queue slightly and does not change what happens to
the request at the back of it.

**The pool lock is still the cost.** A `perf` profile taken under the same load
with the cache on, 4,119 samples, against `run-2026-07-29-pool-lock.md`'s 2,156
with it off:

| Symbol | off | on |
| --- | --- | --- |
| `Mutex::lock_contended` | 20.6% | 18.7% |
| `LivePool::acquire` | 12.3% | 11.7% |
| the pool's `HashMap` entry lookup | 4.7% | 4.8% |
| dropping `WaitGuard` | 4.0% | 4.5% |
| `Notify::poll_notified` | 3.6% | 4.1% |
| `Arc<LivePool>::acquire` | 2.7% | 2.8% |
| `notify_waiters` | 2.2% | 2.2% |
| **the pool and its wakeups** | **~50%** | **~49%** |

The share is flat. That is not a contradiction of the 7% CPU improvement: the
share is of a smaller total, so the absolute lock cost fell roughly in
proportion to the hit share. What it means is that the cache does not change
the shape of `M7.56`'s problem. Contention is a function of how many callers
are queued, and 89% of statements still queue.

**Memory went up 5% per connection**, which is the cache's own bytes divided by
the connection count rather than a per-connection cost. At 64 MiB over 500
connections it is 134 KB each; at 100k connections the same budget is 670 bytes
each. It scales the right way and is not a reason to hesitate.

## What this says about M9

The cache is worth having and it is not the answer to the pool lock.

Seven percent of median latency and seven percent of CPU for a feature that is
off by default and opt-in per tenant is a good trade, particularly for a tenant
whose workload is more read-heavy than this one: the reference workload is 30%
writes, which is close to the worst case for a cache that invalidates on write.

It is not what closes the gap to 100k active connections. `M7.57` is still the
task that matters for that, and this run is more evidence for it rather than
less: half the proxy's CPU is one mutex, and the only thing that moved it was
sending 11% fewer callers at it.

`M9.12` is worth doing on this evidence. The extended protocol is half of every
run and all of it is a miss, so the ceiling roughly doubles if a `Bind`'s
parameters can be read.

## The machine

The same one as every run in this directory, and the same caveat: `--local`
rather than the compose stack, one node, a Postgres on the same host. The
absolute latencies are a saturated database on a laptop and mean nothing. The
comparison is the measurement, and both arms ran within minutes of each other
in the same conditions, alternating so that a machine drifting over the hour
would show up in both.
