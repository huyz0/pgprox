# Holding 100k connections, 28 July 2026

**100,000 client connections on one node, 546 MB of userspace, stable.** The
roadmap's target is 500 MB. This is the first run to get near it, and it
measures one of the three conditions rather than all of them.

## What was run

| | |
| --- | --- |
| Connections | 100,000, from five `loadgen` containers, 120s ramp |
| Workload | `product/perf/workload-hold.yaml`: a transaction every 10 to 15 minutes |
| Duration | 420s |
| Machine | 20 cores, 31 GB, WSL2, everything in containers on one box |

## What it did

| Elapsed | Sockets | Registered | RSS |
| --- | --- | --- | --- |
| 60s | 50,293 | 50,266 | 284 MB |
| 120s | 100,043 | **99,940** | 561 MB |
| 180s | 99,981 | 99,940 | 567 MB |
| 240s | 99,977 | 99,880 | 567 MB |
| 300s | 99,921 | 99,820 | 567 MB |
| 360s | 99,861 | 99,760 | 567 MB |

Baseline 8 MB, so **5,726 bytes per connection** and **546 MB for a hundred
thousand**. Flat from the moment the ramp finished: no leak, no churn, and the
node's own CPU was 365 seconds over the four minutes of sampling, most of it
the ramp.

## What this does and does not say

It says what an open connection costs, which is the question the 500 MB target
is about. This run is 9% over that target.

It says nothing about serving. The workload has a connection think for ten to
fifteen minutes before its first transaction, and the run is seven minutes, so
almost no transactions were attempted: the load clients report "nothing was
attempted", which is correct and is why they report no latency. Added p99 and
the upstream cap, the roadmap's other two conditions, are not demonstrated
here. The 1000-connection runs demonstrate those.

The same 100k connections under the reference workload do not stay up: the
database behind them is one Postgres with a 60-connection cap sharing twenty
cores with five load generators, and the pool answers the overflow with 53300.
That is a fact about this machine, not about the proxy.

## What made it possible

Three fixes today, in the order they were found.

The per-connection cost went from 15,489 bytes to 5,726: a 4 KiB stack array
held across every read, then the startup state that stayed resident for the
life of a connection.

The grant cache had no caller (M7.51). Every connection made its own gRPC call
to the sidecar, and at a hundred thousand of them one h2 connection ran out of
streams and answered every client "authentication service unavailable".

The load generator was hitting its own limits and it looked like the proxy's.
A container has 28,231 ephemeral ports by default and each generator was
opening 20,000 connections, so any churn exhausted it: the error is `Cannot
assign requested address`. The scale override now gives the generators the
whole unprivileged range. And every connection ran a transaction the instant
it connected, so a hundred thousand arrivals meant a hundred thousand
transactions; a connection now thinks before its first one, like a real client.
