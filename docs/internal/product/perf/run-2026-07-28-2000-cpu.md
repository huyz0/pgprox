# 2,000 connections, CPU per statement

`scripts/scale.sh 2000` against the compose stack, on the developer machine
described in `run-2026-07-27-1000-compose.md`. The run M7.46 asked for.

| | |
| --- | --- |
| Connections | 2,000 |
| Transactions | 13,126, 92 refused with `53300` |
| Statements | 37,026, 5,047 on a replica (13%) |
| Upstream connections | 40 of 60 |
| RSS per connection | 12,234 bytes |
| **Proxy CPU** | **157,100 ms over a 30s phase, 4,242 us per statement** |

## What this says about M7.46

Nothing changed. The task recorded 4.5ms of CPU per statement from an ad-hoc
`perf` session, blamed `Wire::consume` draining the front of the read buffer,
and predicted that a cursor would remove it. The cursor is in, the copy per
frame is gone, and the number is 4.2ms.

So the memmove was not the cost. A profile that puts 19% in
`__memmove_avx_unaligned_erms` says where time goes, not why there is so much
of it, and removing one caller of memmove moved the total by less than the
run-to-run spread.

The cursor stays. It is correct, it is cheaper than the drain by construction,
and it paid for itself in the session future once the write overflow buffer was
boxed: 5,064 bytes against 5,096 before. But it is not the answer to this
question and the commit that added it should not be read as if it were.

## What the number actually is

157 seconds of CPU across a 30 second phase is 5.2 cores. At 1,234 statements
a second that is 4.2ms each, against an instruction count of roughly 10us for
the decision path: three orders of magnitude, which is not a hot loop being
slightly slow.

The two candidates that survive this run, neither measured:

- **The connections rather than the statements.** 2,000 tasks each with a
  socket, a timer and a place in the registry cost something per wakeup whether
  or not they have work. The per-statement figure divides all of it by the
  statements, so an idle-connection cost shows up as a per-statement cost. The
  test is to hold the statement rate and change the connection count.
- **The queue.** p99 at this connection count is 25 seconds and the database is
  the queue, so the proxy is spending its time on clients that are waiting. The
  test is the same run against a database that is not saturated, which this
  machine cannot provide.

Both are answered by a run whose two variables move independently, and that is
the next task rather than this one.
