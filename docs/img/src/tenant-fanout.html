Database per tenant, and the three keys that keep them apart

One cluster of the hundred. The tenant is not read from the startup packet; it arrives in the grant the token service returns.

Client sessions
Tens of thousands, one per web thread in flight
JWT → grant
The token service returns the tenant, the backend credentials and the pool policy. pgprox validates no JWT of its own
session → transaction
A connection is borrowed for a transaction and returned at ReadyForQuery, not held for the session
reset on release
Anything a session changed is undone before the connection is reused
Many sessions, few connections.
The pool key is (server, database, role), so a connection is never handed to a session that would have connected as anything else.
One cluster, ~2,000 tenant databases
A pool per key, and one cap across all of them
tenant_acme  /  acme_app

tenant_globex  /  globex_app
A different key, so never the same connection

tenant_2000  /  app_2000
All of them under one max_connections
the pool key server, database and role. The boundary is the database credential, not the tenant name
the cache key tenant, database, role, normalized SQL, bound parameters and search_path: six components, all six required
the grant cache key sha256(token) plus the requested database, never the tenant, so a revoked token cannot ride on another one that is still valid

Adding a tenant adds a database and a pool key. It does not add a connection to every application node in the fleet.
